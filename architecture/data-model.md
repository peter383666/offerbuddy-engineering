# Sprint 1 Data Model

## Purpose

This document describes the schema created by the deployed Flyway migrations. The migrations and mapped entities are the source of truth.

## Overview

Sprint 1 persists three business tables:

```text
users
  user_id (UUID)
      |
      | application-enforced ownership reference
      v
job_applications
  application_id (UUID)
  user_id (UUID)
  job_id (UUID)
      |
      | application-enforced job reference
      v
jobs
  job_id (UUID)
```

`job_applications.user_id` and `job_applications.job_id` are UUID references without database foreign-key constraints or JPA `@ManyToOne` mappings. Services and user-scoped repository queries enforce ownership and existence.

## Identifier Strategy

Every table has two identifier roles:

- an internal `BIGINT GENERATED BY DEFAULT AS IDENTITY` primary key used by persistence
- a public UUID domain identifier exposed by APIs

Public identifiers are:

- `users.user_id`
- `jobs.job_id`
- `job_applications.application_id`

Clients treat UUIDs as opaque values. Internal BIGINT identifiers are not exposed by the API.

## users

A row represents one local OfferBuddy account linked to one external identity.

Important columns:

| Column | Behaviour |
| --- | --- |
| `id` | Internal identity primary key |
| `user_id` | Required, unique public UUID |
| `email` | Required and unique |
| `display_name` | Optional |
| `avatar_url` | Optional |
| `auth_provider` | Required; Google is the Sprint 1 provider |
| `provider_user_id` | Required external provider subject |
| `created_at`, `updated_at` | Required timestamps |

Constraints:

- unique `user_id`
- unique `email`
- unique `(auth_provider, provider_user_id)`

The provider composite uniqueness prevents one Google subject from creating multiple local users.

## jobs

A row contains confirmed job information created or reused when an application is saved.

Important columns:

| Column | Behaviour |
| --- | --- |
| `id` | Internal identity primary key |
| `job_id` | Required, unique public UUID |
| `company_name` | Required |
| `job_title` | Required |
| `location` | Optional |
| `work_type` | Optional; API `employmentType` |
| `work_mode` | Optional; API `workplaceType` |
| `salary_text` | Optional, added by V2 |
| `visa_sponsorship` | Optional, added by V2 |
| `source_platform` | Optional after V2 |
| `external_job_id` | Optional |
| `source_url` | Optional after V2 |
| `description` | Optional |
| `responsibilities` | Optional |
| `requirements` | Optional |
| `created_at`, `updated_at` | Required timestamps |

Constraints and indexes:

- unique `job_id`
- unique `(source_platform, external_job_id)`
- index on `company_name`
- non-unique index on `source_url`

When both source platform and external job ID exist, the database prevents duplicates for that source identity. Source URL lookup and company/title matching are application-level behaviours; there is no unique source-URL or company/title constraint.

## job_applications

A row represents one user's current application state for a job.

Important columns:

| Column | Behaviour |
| --- | --- |
| `id` | Internal identity primary key |
| `application_id` | Required, unique public UUID |
| `user_id` | Required public user UUID reference |
| `job_id` | Required public job UUID reference |
| `status` | Required current status; defaults to `APPLIED` |
| `applied_at` | Required business date |
| `notes` | Optional |
| `created_at`, `updated_at` | Required timestamps |

Constraints and indexes:

- unique `application_id`
- unique `(user_id, job_id)`
- index on `(user_id, applied_at DESC)`

The unique user/job constraint is part of duplicate protection. The application service also rejects an existing user application with matching company name and job title. The API returns `409 DUPLICATE_APPLICATION`.

## Application Status

The persisted status is a string enum with these Sprint 1 values:

- `APPLIED`
- `NO_RESPONSE`
- `INTERVIEW`
- `OFFER`
- `REJECTED`
- `WITHDRAWN`

Only the current status is stored. There is no status-history table.

## Creation Transaction

```text
validate request
  -> reject an existing matching application
  -> find or create Job
  -> create Application in APPLIED status
  -> commit both changes in one transaction
```

A failed application insert does not leave a job created by that transaction.

## Flyway Migrations

| Migration | Effect |
| --- | --- |
| `V1__create_initial_schema.sql` | Creates users, jobs, job_applications, constraints, and initial indexes |
| `V2__align_jobs_and_applications_for_create.sql` | Makes source fields optional, adds salary/visa fields, and adds source URL index |

Deployed migration files are immutable. Future schema changes require a new ordered migration.

## Not Present in Sprint 1

The database does not contain separate tables for:

- companies
- external identities
- parsing jobs or parsing status
- application status history
- analytics/dashboard aggregates
- interviews, resumes, or cover letters
