## 1. Purpose

`Personal Details` allows the user to maintain the basic identifying and contact information that belongs to the authoritative Candidate Profile.

This page answers:

> **What personal/contact information should OfferBuddy use when preparing my applications?**

These values may later appear in Tailored Resume and Cover Letter generation, but they remain Candidate Profile facts.

------

## 2. Scope

### In Scope

- view current personal details;
- edit supported fields;
- validate user input;
- save changes using `profileVersion`;
- handle stale-write conflict;
- return to Candidate Profile Overview;
- preserve existing S2 Web shell and form conventions.

### Out of Scope

- authentication account settings;
- Google account management;
- password/email-login configuration;
- job-specific personal details;
- Resume-specific overrides;
- editing skills/experience/education;
- visa/work-rights editing;
- Application lifecycle;
- automatic AI rewriting;
- multiple Candidate identities/personas.

------

## 9. Field Specification

The final field list must match the frozen Candidate Profile data model and Figma.

At minimum, implementation should treat each visible field according to this pattern:

| Field                  | Type                       | Required                          | Editable                          | Validation / Behaviour                             |
| ---------------------- | -------------------------- | --------------------------------- | --------------------------------- | -------------------------------------------------- |
| First name             | Text                       | Contract-defined                  | Yes                               | Trim surrounding whitespace                        |
| Last name              | Text                       | Contract-defined                  | Yes                               | Trim surrounding whitespace                        |
| Preferred/display name | Text                       | No unless contract says otherwise | Yes                               | Do not overwrite legal/name fields implicitly      |
| Email                  | Email                      | Contract-defined                  | Yes where profile contract allows | Valid email format                                 |
| Phone                  | Text/Tel                   | No unless contract says otherwise | Yes                               | Preserve valid international formats               |
| Location               | Text / structured location | No unless contract says otherwise | Yes                               | Do not infer citizenship/work rights from location |

If Figma/schema contains different exact fields, the frozen contract takes precedence.

------

## 10. Field Behaviour

### Names

Do not silently transform or reorder names based on assumptions about nationality or naming convention.

User-entered values remain authoritative.

### Email

Candidate Profile email and authentication account email may happen to be the same, but they are not automatically the same domain concept.

Do not implement:

```text
change Candidate Profile email
→ change Google/authentication identity
```

unless a separate account contract explicitly requires it.

### Phone

Do not unnecessarily restrict Australian-only formats if the frozen field is general Candidate contact information.

### Location

Location is descriptive Candidate information.

It must not be interpreted as:

- permanent residency;
- citizenship;
- work eligibility;
- sponsorship requirement.

Those belong to Eligibility.

------

## 11. Actions

### Save

**Trigger**

User submits valid changes.

**Request context**

Must include the frozen Candidate Profile OCC requirement, conceptually:

```text
candidate/profile update
+
expected profileVersion
```

### Success

- authoritative Profile is updated;
- meaningful fact revision increments `profileVersion`;
- user sees successful saved state;
- navigate back to Candidate Profile Overview or remain according to frozen Figma flow;
- overview must reflect authoritative returned/reloaded data.

### Validation Failure

Remain on form and associate errors with affected fields.

### Conflict

If expected `profileVersion` is stale:

> explicit conflict; do not overwrite.

### Request Failure

Preserve user-entered form values.

------

### Cancel / Back

Return without applying unsaved changes.

If the form is dirty, use the existing OfferBuddy unsaved-change pattern where available.

Do not silently save.

------

## 12. UI States

### Loading

Profile section is loading.

### Ready

Current values displayed.

### Editing / Dirty

User modified one or more fields.

### Validation Error

Client/server validation failed.

### Saving

- disable duplicate Save;
- show clear saving state.

### Saved

Successful update.

### Save Failure

Keep current user input intact.

### Conflict

Current Profile has changed since the editor was loaded.

Do not automatically merge.

------

## 13. Business Rules

1. Personal Details are part of the authoritative Candidate Profile.
2. One user still has one active Candidate Profile.
3. `candidateId` is not the same thing as `userId`.
4. Personal Details participate in aggregate-level `profileVersion`.
5. There is no separate `personalDetailsVersion`.
6. Meaningful changes increment `profileVersion`.
7. Candidate Profile changes may make derived artifacts stale.
8. Saving Personal Details must not automatically regenerate Match, Resume, or Cover Letter.
9. Candidate Profile email is not automatically authentication identity.
10. Location does not establish work rights.
11. This editor does not modify Eligibility.
12. AI does not need to rewrite Personal Details.
13. Fast Apply remains usable even if some optional Personal Details are missing.

------


------

## 15. Concurrency / Staleness

Candidate Profile uses aggregate-level optimistic concurrency:

```text
profileVersion
```

Example:

```text
Editor loads Profile v14

Another tab updates Skills
→ Profile v15

User saves Personal Details with expected v14
→ conflict
```

The fact that the other change was in Skills does not make silent merge acceptable.

Required UI response:

- explain that Profile changed;
- do not discard local values;
- require refresh/review according to existing conflict UX.

------

## 16. Derived Artifact Impact

A Personal Details change may make derived artifacts stale if the changed fact was part of their provenance.

Potential artifacts:

- Match;
- Tailored Resume;
- Focused Cover Letter.

The Personal Details page must **not** decide to regenerate them automatically.

Correct behaviour:

```text
Personal Details save
        ↓
profileVersion increments
        ↓
existing artifacts may become stale
        ↓
artifact surfaces handle staleness
```

## 23. Security / Privacy

Personal Details are sensitive Candidate-owned data.

Authorization must use backend security context.

The server must determine the authorised Candidate.

The frontend must not be able to change another Candidate by supplying a different `candidateId`.

Avoid unnecessarily exposing Personal Details to:

- Browser Extension;
- RuoYi Admin;
- logging;
- analytics.

Only approved downstream capabilities should receive necessary Candidate data.

------
