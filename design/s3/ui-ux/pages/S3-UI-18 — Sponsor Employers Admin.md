## 1. Purpose

`Sponsor Employers Admin / CRUD` provides an operational RuoYi Admin capability for maintaining the employer sponsorship reference dataset consumed by OfferBuddy.

It answers:

> **Which employers are currently included in OfferBuddy's published sponsorship reference dataset?**

The complete lifecycle is:

```text
RuoYi Admin
     │
     ├── Create
     ├── Edit
     ├── Delete / Disable
     ├── Search
     └── Batch Import
             │
             ▼
       Working Dataset
             │
          Publish
             │
             ▼
     Published Snapshot
        version = N
             │
             ▼
      Browser Extension
             │
      local versioned cache
             │
             ▼
      local employer lookup
```

This page is operational data management.

It is **not** a Candidate-facing sponsorship recommendation system.

------

# 2. Design Principle

OfferBuddy already uses the open-source RuoYi Admin framework.

Therefore:

> **Do not redesign RuoYi.**

Implementation must reuse its native:

> content, fields, actions, states and information hierarchy.

It does **not** instruct the Agent to build a new Admin design system.

# 6. Sponsor Employer Data Model

The UI must follow the actual frozen Sponsor Employer schema.

Conceptually, an employer record may include:

```text
Sponsor Employer
├── canonical employer name
├── aliases
├── domain
├── status
├── source metadata
├── operational metadata
└── timestamps
```

Exact fields come from the frozen backend/database contract.

Agent must not add speculative fields simply because they might be useful later.

------

# 7. Canonical Employer Name

Each Sponsor Employer must have a canonical identity/name according to the frozen model.

Example:

```text
Canonical:
Example Technology Pty Ltd

Aliases:
Example Tech
Example Technology
```

Extension matching can then use controlled known aliases.

The Admin should not encourage maintaining multiple duplicate canonical records for simple name variations.

------

# 8. Aliases

Where supported by the frozen model, aliases allow deterministic matching of recruitment-site employer names.

Example:

```text
Canonical:
ABC Holdings Pty Ltd

Aliases:
ABC
ABC Australia
ABC Holdings
```

Aliases are reference data.

They do not mean:

> all similarly named organisations are the same employer.

Admin users remain responsible for data correctness.

------

# 9. Domain

Where supported:

```text
example.com.au
```

may provide another controlled employer matching signal.

Domain must not automatically be treated as proof that every sub-brand/entity belongs to the same sponsorship record unless the backend matching semantics define it.

------

# 10. Employer Status

If the frozen schema includes active/inactive status:

```text
ACTIVE
INACTIVE
```

or equivalent, the UI should expose it using standard RuoYi status controls.

Inactive means:

> not included as active published sponsor reference data according to domain rules.

It does not necessarily mean:

> employer can never sponsor anyone.

The UI terminology must not overstate the data.

------

> Why is this employer in the dataset?

Possible contract-defined metadata may include:

- source;
- source reference;
- source date;
- import batch;
- notes.

Do not invent provenance fields beyond the actual schema.

# 17. Delete vs Disable

The Agent must use the frozen backend lifecycle.

If Sponsor Employer supports soft status:

> prefer status semantics where required.

If actual delete is supported:

> use RuoYi destructive-action confirmation.

Do not invent hard-delete semantics merely because the table has a Delete button.

Likewise, do not convert a frozen delete operation into soft delete without backend support.

# 18. CRUD Validation

At minimum, validation should protect:

- required canonical name;
- invalid domain format where relevant;
- exact/obvious duplicate canonical records;
- invalid status;
- malformed supported source metadata.

Frontend validation improves UX.

Backend validation remains authoritative.

------

# 19. Duplicate Employer Handling

Obvious duplicate canonical records should not be silently created.

Example:

```text
Example Pty Ltd
example pty ltd
 Example Pty Ltd
```

should be treated according to frozen normalisation rules.

But the system must not aggressively merge:

```text
ABC Australia Pty Ltd
ABC Global Holdings Ltd
```

simply because both contain `ABC`.

No uncontrolled AI fuzzy deduplication belongs in Admin CRUD.

------

# 20. Batch Import Purpose

Because Sponsor Employer reference data may contain many records, Admin must support:

> **Batch Import**

This is an operational productivity feature.

The expected flow is:

```text
Choose file
    ↓
Upload
    ↓
Parse / Validate
    ↓
Import Review
    ↓
Confirm
    ↓
Working Dataset updated
    ↓
Import Result
```

Batch Import does not automatically mean Publish.

------

# 21. Supported Import Format

The Agent must use the format(s) frozen by the backend/import contract.

For example, if CSV/XLSX is supported:

```text
CSV / XLSX
```

Do not add additional formats merely because the frontend upload component supports them.

Provide a template/download mechanism only if it is part of the frozen Admin design/contract.

------

# 22. Import Validation

Import must validate rows before applying them.

Possible categories:

```text
VALID
DUPLICATE
INVALID
CONFLICT
```

Exact backend result codes must be used.

Validation may cover:

- missing employer name;
- invalid domain;
- invalid status;
- duplicate within uploaded file;
- duplicate against existing dataset;
- malformed fields.

Do not rely solely on frontend spreadsheet validation.

------

# 23. Import Review

Before applying a substantial batch, Admin should be able to understand what will happen.

Conceptually:

```text
Import Review

Total rows:       1,250
Valid:            1,180
Duplicates:          42
Invalid:             28

[ Cancel ] [ Confirm Import ]
```

Where final Figma provides row-level review, follow it.

The goal is operational safety, not spreadsheet editing.

------

# 24. Import Error Details

Invalid rows should provide actionable information.

Example:

```text
Row 31
Employer Name: —
Reason: Employer name is required
```

or:

```text
Row 72
Domain: abc
Reason: Invalid domain format
```

Do not expose stack traces, SQL errors or internal exception details.

------

# 25. Import Duplicate Strategy

Duplicate handling must be explicit.

Do not silently overwrite existing records unless the frozen import contract defines an explicit update/upsert mode.

Safer conceptual model:

```text
new record
→ import

duplicate
→ skip / conflict according to chosen frozen policy

invalid
→ reject
```

If the contract supports update-existing:

> Admin must explicitly choose/understand that mode.

Do not hide destructive/updating semantics.

------

# 26. Import Atomicity

Import transaction behaviour must follow the frozen backend design.

The UI must not assume:

> all rows were imported

unless backend reports success accordingly.

If partial import is supported:

> result must show actual counts.

If all-or-nothing import is supported:

> failure must communicate that no changes were committed.

Agent must not invent frontend-only transaction semantics.

------

# 27. Import Result

After processing, show an operational summary.

Conceptually:

```text
Import completed

Created:     1,180
Updated:         0
Skipped:        42
Failed:         28
```

Exact categories follow backend contract.

Admin should be able to return to Sponsor Employers list.

------

# 28. Working Dataset vs Published Snapshot

This distinction is central.

```text
Working Dataset
= current Admin-maintained data

Published Snapshot
= Extension-consumable stable version
```

CRUD/import affects working data.

Extension consumes published data.

This avoids a partially edited Admin dataset immediately changing behaviour across installed Extensions.

------

# 29. Publish Operation

Admin explicitly publishes a new Sponsor Employer snapshot.

Conceptually:

```text
Working Dataset
      ↓
    Publish
      ↓
Validate publishable state
      ↓
Generate immutable logical snapshot
      ↓
version N+1
      ↓
Extensions discover new version
```

Publication should be deliberate.

------

# 30. Publish Confirmation

Publish affects Extension behaviour and should require a clear confirmation.

Conceptually:

```text
Publish Sponsor Employers?

This will create a new version for browser extensions.

Current published version: 18
New version: generated by server

[ Cancel ] [ Publish ]
```

Do not let frontend calculate/assign the authoritative next version.

Backend owns publication/version assignment.

------

# 31. Published Version

The Admin page should make current publication state visible.

For example:

```text
Published version: 18
Published at: ...
```

and where useful:

```text
Working dataset has unpublished changes
```

Exact presentation follows final Figma.

------

# 32. Unpublished Changes

After CRUD/import:

```text
working dataset ≠ last published snapshot
```

Admin should be able to recognise that changes have not yet reached Extension users.

This is more useful than making Publish an invisible technical action.

Do not imply that a successful CRUD save immediately updated all Extensions.

------

# 33. Snapshot Immutability

Once published, a snapshot version should be treated as a stable published representation.

Correct:

```text
v18
→ remains v18

new changes
→ publish v19
```

Incorrect:

```text
modify underlying records
→ silently change contents still labelled v18
```

The exact persistence implementation follows frozen backend/database design, but API semantics must preserve version consistency.

------

# 34. Extension Consumption

Extension should use only the narrow published dataset capability.

Conceptually:

```text
GET current sponsor dataset metadata
       ↓
version = 19

local = 18
       ↓
retrieve published v19
       ↓
replace local snapshot
```

Extension does not call:

```text
Admin Sponsor Employer CRUD APIs
```

ever.

------

# 35. Negative Lookup Behaviour

Once Extension has a valid published snapshot:

```text
Employer not found
      ↓
no sponsor signal
```

It should not call Admin/backend per Job to verify every negative result.

This is why the publication model matters.

------

# 36. Snapshot Payload

The Extension snapshot should contain only fields needed for matching/signalling.

For example, depending on frozen contract:

```text
canonical identity
canonical name
aliases
domain
minimal sponsor status
snapshot version
```

Do not expose unnecessary Admin metadata such as:

- internal notes;
- audit information;
- import batch details;
- admin user information.

Published snapshot is a purpose-specific projection.

------

# 37. Sponsor Signal Semantics

Admin maintains reference data.

It does not determine:

> This Job definitely offers sponsorship.

Therefore even a published positive employer record should result in wording such as:

> sponsorship signal found

rather than:

> sponsorship available

unless the underlying data explicitly supports the stronger claim.

# 44. Concurrency

# 45. Idempotency

Batch import and Publish are operations where accidental duplicate submission can matter.

Use the frozen API idempotency semantics where §3.17 requires `Idempotency-Key`.

But UI disabling is not a replacement for backend idempotency.

# 47. Error States

The page must distinguish at least:

### List Load Failure

RuoYi page remains recoverable.

### CRUD Validation Failure

Keep dialog values.

### CRUD Conflict

Show actionable conflict.

### Import Validation Failure

Show row/result summary.

### Import Processing Failure

Do not imply success.

### Publish Failure

Keep current published snapshot unchanged.

### Permission Failure

Use standard RuoYi behaviour.

------

# 48. Publish Failure Safety

This is important.

If publishing v19 fails:

```text
current published = v18
```

must remain valid.

Do not produce:

```text
published version = v19
but payload incomplete
```

or clear v18 before v19 is ready.

Conceptually:

```text
Build/validate v19
       ↓
success?
  │         │
 yes        no
  │         │
activate    keep v18
 v19
```

------

# 49. Import Failure Safety

Similarly, malformed import must not corrupt the existing working dataset.

Backend transaction boundaries remain authoritative.

Frontend must report the actual result instead of optimistically assuming uploaded rows became valid records.
